# ADR-0012: Codegen and component schema source of truth

**Status:** Accepted  
**Date:** 2026-09-19  
**Related:** `docs/blueprint.md`

## Context

Dart macros were cancelled; runtime reflection is unavailable in Flutter AOT; built-in components would otherwise be described three times (Rust, Dart, JSON Schema).

## Decision

- Behaviour registration, field serializers, and Inspector metadata are generated by **`build_runner`** via `fynkel codegen`; generated files under `lib/generated/` are **committed**. The editor reads only committed metadata and shows a banner when stale; it never runs codegen or game code.
- **Rust structs are the source of truth** for built-in components. Derive macros/attributes emit a component schema from which a Fynkel codegen step generates Dart bindings, wire encoders/decoders (ADR-0004), and JSON Schema.
- **Two generators, one command.** `fynkel codegen` is the single user-facing entry point, but internally runs two independent pipelines with separate incremental caches and test fixtures: (a) the *native schema generator* — Rust component definitions → JSON Schema + Dart native component API + wire codecs; (b) the *behaviour generator* — Dart `@FynkelBehaviour` classes → `build_runner` → factories, field serializers, Inspector metadata. Engine developers run (a) when Rust components change; game developers normally only trigger (b).

## Alternatives considered

- Custom analyzer-based generator: faster, but owning a code generator is scope.
- Manual registration: zero tooling, boilerplate that agents and humans will get wrong.
- JSON schema files as source generating Rust: language-neutral but Rust codegen from JSON adds build complexity.

## Consequences

Adding a built-in component is one Rust edit plus regeneration. `build_runner` latency is accepted; `fynkel codegen` must provide a fast incremental path.
